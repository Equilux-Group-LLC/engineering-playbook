# Equilux LLC — Design System Specification

## 0. Purpose & how to use this document

This document is the single source of truth for Equilux LLC's visual identity. It is written to be read by an AI coding agent (e.g. Claude) before generating or editing any web page, landing page section, banner, deck, or other brand collateral, as well as by a human designer/developer.

Rules for agents consuming this spec:

1. Never invent colors, fonts, or spacing values outside what's defined here. If a needed token doesn't exist, propose an addition rather than freelancing a one-off value.
2. The **Logo & Mark** section (§8) now has an approved wordmark — use it as specified there. The stacked lockup, exact clear-space/minimum-size numbers, and a one-color version are still open; don't invent those, propose them or ask.
3. The **Voice & Tone** section (§10) is a structural skeleton only — headers exist, content does not. Do not fabricate tone/voice content to fill it in; leave it as TBD until populated.
4. Copy-pasteable implementation tokens (CSS custom properties + JSON) are in §11 — prefer those over re-deriving values from the prose tables.
5. **Building anything that supports OS-driven light/dark (a website, an app screen)?** Build from the *semantic* tokens (`bg`, `surface`, `text`, `text-secondary`, `border`, `link`, `accent`) in §3.5/§11, not the literal palette tokens (`navy-900`, `paper`, etc.) directly. The literal tokens never change value; the semantic tokens are what resolve differently per theme. `cta-*` (buttons) are the one exception — they're theme-invariant by design (§3.5).

## 1. Brand foundation

**Name:** Equilux — from *equilux*, the astronomical day on which day and night are of equal length everywhere on Earth (distinct from an equinox). Chosen for two layered meanings:

- **Equal light** — balance across competing elements: strategy and execution, data and people, structure and adaptability.
- **The terminator line** — the boundary where light meets dark on a globe is a natural metaphor for working at the boundary of two worlds.

**Brand pillars** (drive tone and visual choices throughout this spec):

| Pillar | What it means visually |
|---|---|
| Balance | Symmetric layouts where sensible; palette pairs a cool anchor (navy) with a growth color (green) rather than leaning on one dominant hue |
| Analog ↔ Digital | Precise, engineered typography and grid systems (digital) alongside warmer neutral backgrounds and a hand-tuned, non-clinical palette (analog) |
| Data / geospatial pedigree | Coordinate-grid and dashed-line motifs (see §7), monospace accents for data callouts |
| Quiet confidence | Restrained color use, generous whitespace, no gradients/glow effects, no stock-startup clichés |

## 2. Visual identity overview

The identity system has four parts: a color system (§3, including the light/dark semantic layer in §3.5), a type system (§4), a graphic motif language derived from the existing quarter-globe asset (§6), and a logo/mark (§8, finalized). Everything downstream — banners, page layouts, decks — should be built from the tokens in §3/§4/§11, not from ad hoc values.

## 3. Color system

Two brand colors — deep navy and a balanced green — carry the identity, supported by a warm neutral (not stark white) that nods to the "analog" side of the brand, plus a restrained gold used only as a sparing accent for the "light" half of the *equilux* concept.

### 3.1 Palette

| Token | Hex | RGB | Role |
|---|---|---|---|
| `navy-900` | `#0E2238` | 14, 34, 56 | Primary brand color. Headlines on light backgrounds, dark section backgrounds, primary UI chrome |
| `navy-700` | `#1B3A5C` | 27, 58, 92 | Secondary dark — hover states, secondary backgrounds |
| `navy-500` | `#2E5A87` | 46, 90, 135 | Mid-tone navy — links, secondary text on light backgrounds, chart series |
| `green-800` | `#1E5138` | 30, 81, 56 | Deep green — dark-background text/accents, pairs with navy-900 sections |
| `green-600` | `#2F7A54` | 47, 122, 84 | Primary accent. Primary CTAs, active states, key data highlights |
| `green-400` | `#5FAE83` | 95, 174, 131 | Light accent — **decorative/large-scale use only** (see §3.3), chart series, backgrounds behind dark text |
| `gold-500` | `#D9A441` | 217, 164, 65 | "Equal light" accent. Sparing use — badges, small highlights, the literal light-half of the equilux concept; also the logo's X and rule-dot (§8). **Not for body text on light backgrounds** |
| `paper` | `#F7F5F1` | 247, 245, 241 | Primary light background. Warm off-white, not pure white — this is the "analog" neutral |
| `white` | `#FFFFFF` | 255, 255, 255 | Secondary light background, text on dark backgrounds, card surfaces |
| `black` | `#0A0A0A` | 10, 10, 10 | Near-black — matches the source graphic's fill. Use for the graphic motif and maximum-contrast text only; prefer `navy-900` for body copy |
| `gray-700` | `#4A4F55` | 74, 79, 85 | Body text on light backgrounds when full navy is too heavy; secondary/caption text |

### 3.2 Usage ratios

Target roughly **60% neutral (paper/white) — 30% navy — 10% green**, with gold used in the low single digits of any given layout (a badge, an underline, one icon). This keeps the palette calm; it should never look like a green-and-blue gradient wash.

This ratio is stated for the light theme. In dark theme (§3.5), navy stops being a 30%-of-the-page accent and becomes the dominant neutral ground instead — roughly **60% navy (900/700) — 30% paper/white (as text, not fields) — 10% green**, gold still in the low single digits. The two themes swap which color plays "neutral base" vs. "text/accent"; they don't both try to be light.

### 3.3 Verified accessibility (WCAG 2.1)

Contrast ratios were computed directly (relative luminance method), not estimated. All pairs below meet **AA** at minimum for their intended use:

| Foreground | Background | Ratio | Passes |
|---|---|---|---|
| `white` | `navy-900` | 16.1 : 1 | AA + AAA, any text size |
| `white` | `navy-700` | 11.6 : 1 | AA + AAA |
| `white` | `green-800` | 9.2 : 1 | AA + AAA |
| `white` | `green-600` | 5.2 : 1 | AA (normal text) |
| `navy-900` | `paper` / `white` | 14.8 / 16.1 : 1 | AA + AAA |
| `navy-500` | `paper` / `white` | 6.6 / 7.2 : 1 | AA (normal text) |
| `gray-700` | `paper` / `white` | 7.6 / 8.3 : 1 | AA + AAA |
| `green-600` | `paper` / `white` | 4.8 / 5.2 : 1 | AA (normal text, 14px+) |
| `green-800` | `paper` | 8.4 : 1 | AA + AAA |
| `gold-500` | `navy-900` | 7.2 : 1 | AA + AAA |
| `black` | `paper` / `white` | 18.2 / 19.8 : 1 | AA + AAA |

**Fails — do not use for text:** `gold-500` on `paper`/`white` (2.1–2.3 : 1) and `green-400` on `paper`/`white` (2.5–2.7 : 1). Restrict both to decorative use (borders, chart fills, backgrounds behind other text, icon fills at large scale) when placed on light backgrounds. On dark (`navy-900`) backgrounds both are fine for text (`green-400`: 6.0 : 1; verify `gold-500` case by case). The logo's gold X (§8) is a decorative mark, not text, so this restriction doesn't block it.

### 3.4 Do / don't

- Do pair navy with paper/white for primary layouts; reserve full-green backgrounds for accents (a section divider, a callout box), not entire pages.
- Do use gold as a single point of emphasis, never as a background field larger than a badge/button.
- Don't introduce a second blue or a second green outside this palette. Don't use pure `#000000`/`#FFFFFF` for large text blocks — use `navy-900`/`paper` instead for the brand's warmer register.

### 3.5 Semantic layer & dark theme

§3.1's tokens (`navy-900`, `paper`, etc.) are **literal** — fixed hex values that never change meaning. They're fine for a print piece or a single-theme banner. They break the moment something needs to look right in both an OS-light and an OS-dark context, because nothing says *which* literal token plays the role of "the page background" — that role is different in each theme. The fix is a second, smaller set of **semantic** tokens, named by role, that point at different literal tokens depending on theme. Build UI from the semantic tokens; keep the literal ones as the fixed palette they resolve to.

**The inversion decision:** full swap, not a muted "dark gray" theme grafted on. `navy-900` already measures ~14% lightness — it's darker than most products' dark-mode backgrounds already, so it doesn't need a separate near-black invented for it. And a full navy-ground / paper-text dark theme is literally what the logo's **Reversed** lockup (§8) was already built for — dark theme isn't a new direction, it's the brand's own reversed pairing applied system-wide. That's the "how much inverts" answer: background and text fully swap; the brand hues (green, gold) shift only as far as accessibility requires, covered token-by-token below.

| Semantic token | Role | Light value | Dark value | Why |
|---|---|---|---|---|
| `bg` | Page background | `paper` | `navy-900` | Full swap — see above |
| `surface` | Card/panel, one step off the page background | `white` | `navy-700` | `navy-700` is ~10pt lighter than `navy-900` (relative luminance 0.040 vs 0.015) — enough to read as "raised" without a new gray |
| `text` | Primary text | `navy-900` | `paper` | Mirrors the logo's Primary/Reversed wordmark color exactly |
| `text-secondary` | Secondary/caption text | `gray-700` | `paper` at 72% opacity | No literal "light gray" token exists for dark grounds; 72% paper is a documented, reproducible formula, not a one-off pick — verified 6.4:1 on `surface`, 8.2:1 on `bg` |
| `border` | Hairline borders/dividers | `navy-900` at 10% opacity | `paper` at 14% opacity | Same rule both directions: border = `text` color at low opacity, so it's never invented per-theme |
| `link` | Inline text links | `navy-500` | `green-400` | Light theme's link uses the cool/navy hue (`navy-500` fails as a dark-ground token below AA); dark theme's link uses the growth/green hue (`green-600` only manages 3.1:1 on `navy-900`, under AA — `green-400` clears it at 6.0:1) |
| `accent` | Active states, selected nav item, focus rings | `green-600` | `green-400` | Same reasoning as `link` — `green-600` doesn't clear AA as a foreground color on `navy-900` |
| `highlight` | Gold "equal light" accent — badges, single emphasis | `gold-500` (decorative only, still not for text) | `gold-500` (decorative **and** text-safe — 7.2:1 on `navy-900`) | Same hex both themes; dark theme is actually less restrictive because gold reads better on navy than on paper |

**Theme-invariant — do not swap:** `cta-bg` (`green-600`), `cta-bg-hover` (`green-800`), `cta-text` (`white`). A primary button is a self-contained color pair (white text already clears AA on `green-600` regardless of what's behind the button), so it stays identical in both themes rather than picking up a second set of hover states to maintain. Treat filled buttons and badges as "brand-colored objects," not page surface — they don't participate in the bg/text inversion.

**Verified contrast (dark theme, computed the same way as §3.3):**

| Foreground | Background | Ratio | Passes |
|---|---|---|---|
| `paper` (text) | `navy-900` (bg) | 14.8 : 1 | AA + AAA |
| `paper` (text) | `navy-700` (surface) | 10.7 : 1 | AA + AAA |
| `paper` @72% (text-secondary) | `navy-900` (bg) | 8.2 : 1 | AA + AAA |
| `paper` @72% (text-secondary) | `navy-700` (surface) | 6.4 : 1 | AA + AAA |
| `green-400` (link/accent) | `navy-900` (bg) | 6.0 : 1 | AA (normal text) |
| `green-400` (link/accent) | `navy-700` (surface) | 4.4 : 1 | AA (normal text) |
| `gold-500` (highlight) | `navy-900` (bg) | 7.2 : 1 | AA + AAA |
| `gold-500` (highlight) | `navy-700` (surface) | 5.2 : 1 | AA (normal text) |

**Fails — confirmed, don't use:** `green-600` as a text/foreground color on `navy-900` (3.1:1) or `navy-700` (2.2:1) — that's exactly why `link`/`accent` switch to `green-400` in dark theme rather than reusing the light theme's `green-600`.

**What doesn't change:** the graphic motif (§6) already specified dashed lines and partial-circle crops over *either* navy or paper grounds — no new dark-mode motif guidance needed. Photography guidance (§7) is theme-neutral. Typography (§4) is theme-neutral — only the *color* a headline is set in changes (via `text`), never the family, weight, or scale.

## 4. Typography

**Direction: modern geometric.** Clean, precise, technically confident — matches the data/product-engineering positioning without tipping into cold or sterile.

All families below are free and open-source (SIL Open Font License 1.1 or Apache 2.0), hosted on Google Fonts, self-hostable, and require **no license purchase or attribution obligation** for commercial use.

| Role | Family | License | Source |
|---|---|---|---|
| Display / Headlines | **Space Grotesk** | SIL OFL 1.1 | fonts.google.com/specimen/Space+Grotesk |
| Body / UI | **Inter** | SIL OFL 1.1 | fonts.google.com/specimen/Inter |
| Data / mono accent | **IBM Plex Mono** | SIL OFL 1.1 | fonts.google.com/specimen/IBM+Plex+Mono |

Rationale: Space Grotesk is a geometric sans with just enough character in its letterforms (the squared-off, slightly irregular curves) to avoid looking generic, and reads as engineered rather than corporate — this is also the logo's typeface (§8). Inter is the highly legible, neutral workhorse for body copy and UI at any size. IBM Plex Mono is used sparingly — stat callouts, data labels, coordinates, code — as a nod to the geospatial/data background; it is a tertiary accent, not a primary text face.

### 4.1 Import (self-host preferred; CDN fallback shown)

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Space+Grotesk:wght@500;600;700&family=Inter:wght@400;500;600&family=IBM+Plex+Mono:wght@500&display=swap" rel="stylesheet">
```

For production, download the woff2 files from Google Fonts and self-host to avoid a third-party request; the license permits this.

### 4.2 Type scale

Fluid-friendly scale, base 16px, ratio ~1.25:

| Token | Size | Line-height | Family | Weight |
|---|---|---|---|---|
| `display-xl` | 56px / 3.5rem | 1.1 | Space Grotesk | 600 |
| `display-lg` | 40px / 2.5rem | 1.15 | Space Grotesk | 600 |
| `heading-lg` | 32px / 2rem | 1.2 | Space Grotesk | 600 |
| `heading-md` | 24px / 1.5rem | 1.3 | Space Grotesk | 500 |
| `heading-sm` | 19px / 1.1875rem | 1.4 | Space Grotesk | 500 |
| `body-lg` | 18px / 1.125rem | 1.6 | Inter | 400 |
| `body-md` | 16px / 1rem | 1.6 | Inter | 400 |
| `body-sm` | 14px / 0.875rem | 1.5 | Inter | 400 |
| `label` | 13px / 0.8125rem | 1.4 | Inter | 600 (uppercase, +0.04em tracking) |
| `data` | 15px / 0.9375rem | 1.4 | IBM Plex Mono | 500 |

### 4.3 Usage rules

- Never use Space Grotesk below 19px — it loses legibility at small sizes; drop to Inter.
- Headlines are set in `navy-900` on light backgrounds, `white` or `paper` on dark. Never set Space Grotesk headlines in `gold-500` or `green-400` (contrast + legibility).
- IBM Plex Mono is reserved for genuinely data-like content (numbers, stats, coordinates, code, labels like "18% ↑"), not general emphasis.

## 6. Graphic motif & imagery language

The existing brand asset — a quarter-section of a globe, solid black fill, with a white dashed latitude/longitude grid — is the seed for the brand's recurring graphic language, independent of the wordmark logo (§8).

**Derived motif rules, usable now:**

- **Dashed grid lines** (lat/long-style) as a subtle background texture, section divider, or overlay on photography — evokes coordinate systems / geospatial data without needing an actual map. Use at low opacity (10–20%) over navy or paper backgrounds; never at full black/white contrast except in the source asset itself.
- **Quarter/partial circular crops** — cropping circular or arc shapes at a frame edge (as the source graphic does) is a usable compositional device for section dividers, image masks, and background shapes, echoing "a partial view of something larger."
- **High contrast, no gradients** — the source asset is pure black/white with no shading or gradient. Carry that flatness into all brand graphics; avoid drop shadows, glows, or gradient fills anywhere in the system.
- Recolor the motif using palette tokens: e.g., dashed grid in `gold-500` or `green-600` over a `navy-900` field for a section background. This motif is a separate decorative language from the logo — the two aren't required to appear together.

**Approved versions:**

| Version | "equilu" | X + dot | Rule | Background |

| Reversed | `paper` | `gold-500` | `paper` | `navy-900` |

## 9. Components (general principles)

Full component library is out of scope for this pass; when generating UI, apply these principles using the tokens above rather than inventing new ones. Written against the **semantic** tokens (§3.5) so they hold in both themes without a separate dark-mode variant to maintain:

- **Buttons (primary):** `cta-bg` fill, `cta-text` text, `radius-sm`, hover → `cta-bg-hover`. These are the literal `green-600`/`white`/`green-800` in *both* themes (§3.5) — a filled button doesn't invert. **(secondary):** `text` color 1.5px border, `text` color label, transparent fill, hover → fill `text` / label `bg` (a local swap of the two tokens, which is why it self-adapts per theme without a separate rule).
- **Cards:** `surface` on `bg` page background to create gentle layering without shadows; 1px `text` border at 10% opacity (light) / `border` token (dark, already 14% — see §3.5), `radius-md`.
- **Links:** `link` color, underline on hover, never `accent`/`highlight` alone for inline text links (contrast) — and never the *other* theme's link hue (e.g. don't hardcode `navy-500` into a dark-mode component).
- **Dividers/section breaks:** thin dashed rule referencing the graphic motif (§6), not a solid line; motif already specifies both navy- and paper-ground treatments, so no separate dark variant needed.

## 11. Implementation tokens

### 11.1 CSS custom properties

Literal palette tokens never change value. Semantic tokens are layered on top and are what components should reference; they resolve differently per theme via the three-block pattern below — bare `:root` sets the light (default) values, `prefers-color-scheme` handles OS-driven dark mode, and `[data-theme="dark"]` lets a manual in-page toggle override the OS setting if one is ever added. Every semantic token is declared in the bare `:root` block first — a token defined only inside a media/`[data-theme]` block silently fails to apply in the un-stamped default state.

```css
:root {
  color-scheme: light dark;

  /* Literal palette — fixed, never themed */
  --eqx-navy-900: #0E2238;
  --eqx-navy-700: #1B3A5C;
  --eqx-navy-500: #2E5A87;
  --eqx-green-800: #1E5138;
  --eqx-green-600: #2F7A54;
  --eqx-green-400: #5FAE83;
  --eqx-gold-500: #D9A441;
  --eqx-paper: #F7F5F1;
  --eqx-white: #FFFFFF;
  --eqx-black: #0A0A0A;
  --eqx-gray-700: #4A4F55;

  /* Semantic layer — LIGHT theme (default) */
  --eqx-bg: var(--eqx-paper);
  --eqx-surface: var(--eqx-white);
  --eqx-text: var(--eqx-navy-900);
  --eqx-text-secondary: var(--eqx-gray-700);
  --eqx-border: rgba(14, 34, 56, 0.10);   /* navy-900 @ 10% */
  --eqx-link: var(--eqx-navy-500);
  --eqx-accent: var(--eqx-green-600);
  --eqx-highlight: var(--eqx-gold-500);

  /* Theme-invariant — same in both themes, see §3.5 */
  --eqx-cta-bg: var(--eqx-green-600);
  --eqx-cta-bg-hover: var(--eqx-green-800);
  --eqx-cta-text: var(--eqx-white);

  /* Type */
  --eqx-font-display: 'Space Grotesk', system-ui, sans-serif;
  --eqx-font-body: 'Inter', system-ui, sans-serif;
  --eqx-font-mono: 'IBM Plex Mono', ui-monospace, monospace;

  /* Spacing */
  --eqx-space-1: 4px;
  --eqx-space-2: 8px;
  --eqx-space-3: 12px;
  --eqx-space-4: 16px;
  --eqx-space-5: 24px;
  --eqx-space-6: 32px;
  --eqx-space-7: 48px;
  --eqx-space-8: 64px;
  --eqx-space-9: 96px;

  /* Radius */
  --eqx-radius-sm: 4px;
  --eqx-radius-md: 8px;
  --eqx-radius-lg: 16px;
}

/* Semantic layer — DARK theme, OS-driven, unless an explicit light choice wins */
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) {
    --eqx-bg: var(--eqx-navy-900);
    --eqx-surface: var(--eqx-navy-700);
    --eqx-text: var(--eqx-paper);
    --eqx-text-secondary: rgba(247, 245, 241, 0.72);   /* paper @ 72% */
    --eqx-border: rgba(247, 245, 241, 0.14);           /* paper @ 14% */
    --eqx-link: var(--eqx-green-400);
    --eqx-accent: var(--eqx-green-400);
    --eqx-highlight: var(--eqx-gold-500);              /* same hex, less restricted use — see §3.5 */
  }
}

/* Manual override, e.g. an in-page theme toggle — optional, only needed if you add one */
:root[data-theme="dark"] {
  --eqx-bg: var(--eqx-navy-900);
  --eqx-surface: var(--eqx-navy-700);
  --eqx-text: var(--eqx-paper);
  --eqx-text-secondary: rgba(247, 245, 241, 0.72);
  --eqx-border: rgba(247, 245, 241, 0.14);
  --eqx-link: var(--eqx-green-400);
  --eqx-accent: var(--eqx-green-400);
  --eqx-highlight: var(--eqx-gold-500);
}

body {
  background: var(--eqx-bg);
  color: var(--eqx-text);
}
```
